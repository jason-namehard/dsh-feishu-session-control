# 设计调研摘要

最后更新：2026-09-09。

历史上游调研可从 Git 历史查看；本文件只保留当前决策的依据。

## 为什么使用进程内 host adapter

DSH `0.1.2-rc.1` 的 Web 认证和内部 RPC 会变化。插件既然已经运行在 DSH 宿主进程中，直接通过宿主
services 管理 session，可以减少浏览器 token、HTTP 方法名和 events mux 三类兼容风险。

## 为什么 Web session 默认独立

用户在电脑端创建的 session 不一定需要远程控制。全量镜像会造成飞书通知泛滥、审批入口反客为主，并把
本地对话内容暴露到手机或群聊。按飞书 scope 显式连接更符合最小披露原则。

## 为什么需要 half/full

单一“绑定”状态无法同时满足两种需求：

- 飞书发任务、电脑完整执行，但电脑之后的独立操作保持本地；
- 用户离开电脑后，仍希望同一 session 的电脑端后续回合抄送手机。

因此连接记录持久化 `half|full`，默认 half，只有用户显式 `/switch` 才启用 full。

## 为什么不回填历史

切换 session 的用户通常已经知道目标上下文。自动回填既占手机聊天空间，也可能披露敏感历史。正确做法
是把事件游标推进到绑定快照，只投影之后的新事件。

## 为什么移除独立工具权限门

DSH 已有原生 sandbox 和 approval。飞书插件再按工具名实施一次 `pwsh/write/read` 门会造成重复审批，且
Web 与飞书行为不一致。当前方案只镜像 DSH 已创建的审批，并允许 Web 或飞书任一端回答。

## 为什么移除离线接管

离线接管会让“停止 DSH”不再等于停止远程入口，也会把本地 session 的消息和审批意外推送到飞书。当前
边界改为 DSH 与飞书同生命周期，由用户通过托盘主动启动、重启和退出。
